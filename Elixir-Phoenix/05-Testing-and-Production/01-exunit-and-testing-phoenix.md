# 01 · ExUnit and testing Phoenix

> **Plain English:** Tests are small programs that check your code works and keeps working. Elixir's built-in test tool, ExUnit, runs tests **in parallel**, even ones that use the database, because each test works inside its own transaction that's thrown away afterwards, like a sandbox that resets after every game.

## 1. ExUnit basics

> **In short:** Tests are `.exs` files in `test/`. `use ExUnit.Case`, write `test "name" do ... end`, and assert with `assert`/`refute`. Run them with `mix test`.

```elixir
defmodule MyApp.MathTest do
  use ExUnit.Case, async: true       # this module's tests run concurrently with other async modules

  describe "add/2" do
    test "adds numbers" do
      assert MyApp.Math.add(1, 2) == 3
    end

    test "pattern-matching assertions" do
      assert {:ok, %{id: id}} = MyApp.Thing.create()   # assert with a pattern: binds id
      assert is_integer(id)
    end
  end

  test "raises" do
    assert_raise ArithmeticError, fn -> 1 / 0 end
  end

  test "messages" do
    send(self(), :hello)
    assert_receive :hello            # waits up to 100 ms by default
    refute_received :other
  end
end
```

Setup and context:

```elixir
setup do
  user = %{name: "A"}
  {:ok, user: user}                  # merged into the test context
end

test "uses context", %{user: user} do
  assert user.name == "A"
end

@tag :slow
test "slow thing", do: ...
```

Commands:

```bash
mix test                          # all tests
mix test test/my_app/tasks_test.exs:42
mix test --failed                 # re-run only the failures
mix test --only slow / --exclude slow
mix test --cover                  # coverage report
mix test --stale                  # only tests affected by changed code
mix test --trace                  # run one at a time with detailed output
```

`assert` failures print a helpful diff of left vs right, so there's no need for many assertion helpers.

## 2. The Ecto SQL sandbox: concurrent DB tests

> **In short:** Each test runs inside a DB transaction that's rolled back at the end, so tests can run **in parallel** against the same database without interfering with each other.

This is set up for you in `test/test_helper.exs` and `test/support/data_case.ex`:

```elixir
# test_helper.exs
ExUnit.start()
Ecto.Adapters.SQL.Sandbox.mode(MyApp.Repo, :manual)
```

Processes you spawn in a test (Tasks, GenServers, LiveViews) need access to the test's DB connection. `async: true` tests use "ownership", and the `$callers` chain plus `Sandbox.allow/3` handle it. Phoenix and LiveView tests are wired up already. If you start your own GenServer that hits the DB, either allow it explicitly or start it with `start_supervised!`.

## 3. Test cases generated by Phoenix

| Case | Use for | Gives you |
| --- | --- | --- |
| `MyApp.DataCase` | Context and schema tests | Sandbox, `errors_on/1` helper |
| `MyAppWeb.ConnCase` | Controller, API and LiveView tests | A `conn`, plus `register_and_log_in_user` (from gen.auth) |
| `MyAppWeb.ChannelCase` | Channel tests | Socket helpers |

`errors_on/1` turns a changeset's errors into a map: `%{title: ["can't be blank"]}`.

## 4. Testing a context

> **In short:** This is where most of your tests should live. They're fast, need no HTTP, and test the business rules directly.

```elixir
defmodule MyApp.TasksTest do
  use MyApp.DataCase, async: true
  alias MyApp.Tasks
  import MyApp.AccountsFixtures
  import MyApp.TasksFixtures

  setup do
    %{scope: user_scope_fixture()}
  end

  describe "create_task/2" do
    test "with valid data creates a task", %{scope: scope} do
      assert {:ok, task} = Tasks.create_task(scope, %{title: "Learn Ecto"})
      assert task.title == "Learn Ecto"
      assert task.user_id == scope.user.id
      refute task.done
    end

    test "requires a title", %{scope: scope} do
      assert {:error, changeset} = Tasks.create_task(scope, %{title: ""})
      assert %{title: ["can't be blank"]} = errors_on(changeset)
    end
  end

  test "users can't see each other's tasks", %{scope: scope} do
    other = user_scope_fixture()
    task = task_fixture(other)
    assert_raise Ecto.NoResultsError, fn -> Tasks.get_task!(scope, task.id) end
  end

  test "broadcasts on create", %{scope: scope} do
    Tasks.subscribe_tasks(scope)
    {:ok, task} = Tasks.create_task(scope, %{title: "x"})
    assert_receive {:created, ^task}
  end
end
```

### Fixtures

```elixir
# test/support/fixtures/tasks_fixtures.ex
defmodule MyApp.TasksFixtures do
  def task_fixture(scope, attrs \\ %{}) do
    attrs = Enum.into(attrs, %{title: "Task #{System.unique_integer([:positive])}"})
    {:ok, task} = MyApp.Tasks.create_task(scope, attrs)
    task
  end
end
```

The **ExMachina** library provides factory-style test data (`insert(:task)`), if you prefer factories.

## 5. Testing controllers and JSON APIs

```elixir
defmodule MyAppWeb.Api.TaskControllerTest do
  use MyAppWeb.ConnCase, async: true

  setup %{conn: conn} do
    user = MyApp.AccountsFixtures.user_fixture()
    token = MyApp.Accounts.create_api_token(user)
    conn = conn |> put_req_header("accept", "application/json") |> put_req_header("authorization", "Bearer #{token}")
    %{conn: conn, user: user}
  end

  test "POST /api/tasks creates", %{conn: conn} do
    conn = post(conn, ~p"/api/tasks", task: %{title: "From API"})
    assert %{"id" => id} = json_response(conn, 201)["data"]

    conn = get(conn, ~p"/api/tasks/#{id}")
    assert %{"title" => "From API"} = json_response(conn, 200)["data"]
  end

  test "POST /api/tasks with invalid data returns 422", %{conn: conn} do
    conn = post(conn, ~p"/api/tasks", task: %{title: ""})
    assert json_response(conn, 422)["errors"] != %{}
  end

  test "401 without a token" do
    conn = build_conn() |> get(~p"/api/tasks")
    assert json_response(conn, 401)
  end
end
```

HTML controllers: `html_response(conn, 200) =~ "Tasks"`, `redirected_to(conn) == ~p"/tasks"`.

LiveView tests are covered in [04-LiveView/03](../04-LiveView/03-streams-pubsub-uploads-hooks.md).

## 6. Mocking external services with Mox

> **In short:** Define a behaviour, use the real module in prod and a Mox mock in tests, and set expectations per test. It's concurrency-safe.

```elixir
# lib/my_app/weather.ex
defmodule MyApp.Weather do
  @callback current(city :: String.t()) :: {:ok, map()} | {:error, term()}
  def current(city), do: impl().current(city)
  defp impl, do: Application.get_env(:my_app, :weather_client, MyApp.Weather.HTTP)
end

# test/test_helper.exs
Mox.defmock(MyApp.WeatherMock, for: MyApp.Weather)
Application.put_env(:my_app, :weather_client, MyApp.WeatherMock)

# test
import Mox
setup :verify_on_exit!

test "shows weather" do
  expect(MyApp.WeatherMock, :current, fn "Kochi" -> {:ok, %{temp: 31}} end)
  assert {:ok, %{temp: 31}} = MyApp.Weather.current("Kochi")
end
```

For HTTP-level stubbing, **Req** has built-in test plugs (`Req.Test`), and **Bypass** runs a fake HTTP server.

## 7. What to test, and how much

> **In short:** Context tests for business rules (most of them), a few controller and LiveView tests per feature for wiring, and one or two end-to-end checks.

- Test **behaviour**, not implementation (call public context functions, not private helpers).
- Test the authorization cases (another user's data).
- Test the error paths (`{:error, changeset}`).
- Keep `async: true` everywhere you can.
- CI: `mix format --check-formatted`, `mix compile --warnings-as-errors`, `mix credo`, `mix test`.

## Exercises

1. Write context tests for create, update, delete and list in your trial project, including a "can't see other users' tasks" test.
2. Write JSON API tests for 201, 422 and 401.
3. Add a behaviour plus a Mox mock for an external API (e.g. a fake "AI task suggestions" service).
4. Run `mix test --cover` and aim for most context functions to be covered.

## Interview questions

<details>
<summary>How can Elixir tests hit the database concurrently?</summary>

The Ecto SQL Sandbox wraps each test in its own database transaction on its own checked-out connection, and rolls it back at the end. With `async: true`, test modules run in parallel without seeing each other's data. Processes spawned by a test can be allowed to use its connection (automatically via `$callers`, or with `Sandbox.allow/3`).

</details>

<details>
<summary>How do you mock in Elixir?</summary>

Mocks follow explicit contracts: define a behaviour, resolve the implementation from config, and in tests use Mox to define a mock that implements the behaviour, with `expect`/`stub` per test. Mox expectations are scoped to the test process, so async tests stay safe. Global monkey-patching is avoided on purpose.

</details>
