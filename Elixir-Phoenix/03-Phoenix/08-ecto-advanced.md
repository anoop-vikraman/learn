# 08 · Ecto advanced: relationships, upserts, dynamic queries, locking and more

> **Plain English:** lesson 03 covered the basics: save, load, validate. This lesson covers the situations every real app hits: tags (many-to-many), storing JSON, "insert or update", search filters built from user choices, preventing two people from overwriting each other, UUIDs, soft deletes and multi-tenant apps.

## 1. Associations, all of them

> **In short:** `belongs_to` (this row holds the foreign key), `has_one`/`has_many` (the other table holds it), `many_to_many` (a join table in between), and `has_many :through` (reach across an association).

```elixir
schema "projects" do
  field :name, :string
  belongs_to :owner, MyApp.Accounts.User              # projects.owner_id
  has_many :tasks, MyApp.Tasks.Task                   # tasks.project_id
  has_one :settings, MyApp.Projects.Settings
  has_many :comments, through: [:tasks, :comments]    # reach comments via tasks
  many_to_many :members, MyApp.Accounts.User,
    join_through: MyApp.Projects.Membership,          # a schema for the join table (it can hold extra fields like role)
    on_replace: :delete
  timestamps()
end
```

### Many-to-many: tags on tasks

```elixir
# migration
create table(:tags) do
  add :name, :string, null: false
end
create unique_index(:tags, [:name])

create table(:tasks_tags, primary_key: false) do
  add :task_id, references(:tasks, on_delete: :delete_all), null: false
  add :tag_id, references(:tags, on_delete: :delete_all), null: false
end
create unique_index(:tasks_tags, [:task_id, :tag_id])
```

```elixir
# schema
many_to_many :tags, MyApp.Tasks.Tag, join_through: "tasks_tags", on_replace: :delete

# set a task's tags (replace the whole list)
def put_tags(task, tag_names) do
  tags = Enum.map(tag_names, &get_or_create_tag!/1)

  task
  |> Repo.preload(:tags)
  |> Ecto.Changeset.change()
  |> Ecto.Changeset.put_assoc(:tags, tags)
  |> Repo.update()
end
```

**`put_assoc` vs `cast_assoc`:**
- `put_assoc/3`: you already have the structs or records (e.g. existing tags). You set the association directly.
- `cast_assoc/3`: the data comes from **user params** (a nested form). Each child goes through its own changeset.

**`on_replace`** says what happens to children removed from the list: `:raise` (default), `:delete`, `:nilify`, `:update` or `:mark_as_invalid`.

## 2. Embedded schemas: JSON inside a row

> **In short:** `embeds_one`/`embeds_many` store structured data in a single JSONB column, validated with its own changeset. That's handy for settings, addresses, or a list of checklist items.

```elixir
defmodule MyApp.Tasks.ChecklistItem do
  use Ecto.Schema
  import Ecto.Changeset

  @primary_key false          # or keep an autogenerated id to track items in forms
  embedded_schema do
    field :text, :string
    field :done, :boolean, default: false
  end

  def changeset(item, attrs), do: item |> cast(attrs, [:text, :done]) |> validate_required([:text])
end

# in Task:
embeds_many :checklist, MyApp.Tasks.ChecklistItem, on_replace: :delete
# migration: add :checklist, :map, default: "[]"   (JSONB in Postgres)

# in Task.changeset:
|> cast_embed(:checklist)
```

When to embed vs use a separate table: **embed** data that is always loaded with its parent and never queried on its own. Use a **table** when you need to query it, join it or update items independently.

`embedded_schema` with no table is also how you validate forms that aren't stored (a contact form, search filters):

```elixir
defmodule MyApp.Search do
  use Ecto.Schema
  import Ecto.Changeset

  embedded_schema do
    field :q, :string
    field :status, Ecto.Enum, values: [:todo, :doing, :done]
    field :due_before, :date
  end

  def changeset(params) do
    %__MODULE__{} |> cast(params, [:q, :status, :due_before]) |> validate_length(:q, max: 100)
  end

  def parse(params), do: params |> changeset() |> apply_action(:validate)   # {:ok, struct} | {:error, cs}
end
```

### Schemaless changesets (even lighter)

```elixir
types = %{email: :string, age: :integer}
{%{}, types}
|> Ecto.Changeset.cast(params, Map.keys(types))
|> Ecto.Changeset.validate_required([:email])
|> Ecto.Changeset.apply_action(:insert)
```

## 3. Upserts: insert, or update if it exists

> **In short:** `on_conflict` + `conflict_target` let the database do "insert or update" in one atomic query, with no race condition.

```elixir
# Insert a tag, or do nothing if the name already exists
Repo.insert(%Tag{name: "urgent"}, on_conflict: :nothing, conflict_target: :name)
# careful: with :nothing you get a struct with id: nil back when there's a conflict

# Insert, or update some fields on conflict
Repo.insert(
  changeset,
  on_conflict: {:replace, [:title, :updated_at]},
  conflict_target: [:user_id, :external_id],
  returning: true
)

# Increment a counter atomically on conflict
Repo.insert(
  %PageView{path: "/home", count: 1},
  on_conflict: [inc: [count: 1]],
  conflict_target: :path
)

# Bulk upsert (fast imports)
Repo.insert_all(Product, rows,
  on_conflict: {:replace_all_except, [:id, :inserted_at]},
  conflict_target: :sku
)
```

`insert_all` skips changesets and autogenerated timestamps, so add `inserted_at`/`updated_at` to each row yourself.

## 4. Dynamic queries: filters from user input

> **In short:** Build `where` conditions piece by piece with `dynamic/2`, then plug them into one query. This is the clean way to do search pages with optional filters.

```elixir
def search_tasks(scope, filters) do
  Task
  |> where(user_id: ^scope.user.id)
  |> where(^build_filters(filters))
  |> order_by(^sort_order(filters["sort"]))
  |> Repo.all()
end

defp build_filters(filters) do
  Enum.reduce(filters, dynamic(true), fn
    {"q", q}, acc when q != "" -> dynamic([t], ^acc and ilike(t.title, ^"%#{q}%"))
    {"status", s}, acc when s in ~w(todo doing done) -> dynamic([t], ^acc and t.status == ^String.to_existing_atom(s))
    {"overdue", "true"}, acc -> dynamic([t], ^acc and t.due_on < ^Date.utc_today() and t.status != :done)
    _, acc -> acc
  end)
end

defp sort_order("due"), do: [asc: :due_on]
defp sort_order("title"), do: [asc: :title]
defp sort_order(_), do: [desc: :inserted_at]
```

The **Flop** library packages filtering, sorting and pagination (and has LiveView components) if you'd rather not hand-roll this.

## 5. Advanced queries

### Subqueries

```elixir
latest = from c in Comment, group_by: c.task_id, select: %{task_id: c.task_id, last_at: max(c.inserted_at)}

from t in Task,
  join: l in subquery(latest), on: l.task_id == t.id,
  select: {t.title, l.last_at}
```

### Selecting into maps or structs, and `select_merge`

```elixir
from t in Task, select: map(t, [:id, :title])
from t in Task,
  left_join: c in assoc(t, :comments),
  group_by: t.id,
  select_merge: %{comment_count: count(c.id)}    # fills a virtual field
```

### Named bindings (for composable joins)

```elixir
query = from t in Task, as: :task, join: p in assoc(t, :project), as: :project
where(query, [project: p], p.archived == false)
```

### Aggregates and window functions

```elixir
Repo.aggregate(Task, :count)
Repo.aggregate(from(o in Order, where: o.paid), :sum, :total)

from t in Task,
  select: %{title: t.title, rank: over(row_number(), :by_project)},
  windows: [by_project: [partition_by: t.project_id, order_by: [desc: t.priority]]]
```

### Full-text search (Postgres)

```elixir
from t in Task,
  where: fragment("to_tsvector('english', ?) @@ plainto_tsquery('english', ?)", t.title, ^term)
```

For speed, add a generated `tsvector` column with a GIN index.

### Streaming huge result sets

```elixir
Repo.transaction(fn ->
  Task
  |> where([t], t.inserted_at < ^cutoff)
  |> Repo.stream(max_rows: 500)
  |> Stream.each(&archive/1)
  |> Stream.run()
end, timeout: :infinity)
```

`Repo.stream` must run inside a transaction.

## 6. Concurrency control: optimistic and pessimistic locking

> **In short:** If two users edit the same record at once, the last save silently wins. **Optimistic locking** detects the conflict with a version number. **Pessimistic locking** (`FOR UPDATE`) blocks other writers while you work.

### Optimistic: a version column

```elixir
# migration: add :lock_version, :integer, default: 1
field :lock_version, :integer, default: 1

def changeset(task, attrs) do
  task |> cast(attrs, [:title]) |> optimistic_lock(:lock_version)
end
```

If someone saved in between, `Repo.update` raises `Ecto.StaleEntryError`. Catch it and tell the user "this task changed, please reload". This suits collaborative editing, where conflicts are rare.

### Pessimistic: lock the row inside a transaction

```elixir
Repo.transact(fn ->
  account = Repo.one!(from a in Account, where: a.id == ^id, lock: "FOR UPDATE")
  if account.balance >= amount do
    account |> Account.changeset(%{balance: account.balance - amount}) |> Repo.update()
  else
    {:error, :insufficient_funds}
  end
end)
```

Other transactions trying to lock the same row **wait** until this one commits. Use it for money, inventory and anything where a check-then-update must be atomic.

### Atomic updates without reading first

```elixir
from(p in Product, where: p.id == ^id and p.stock > 0)
|> Repo.update_all(inc: [stock: -1])
# returns {1, nil} if it decremented, {0, nil} if out of stock: no race possible
```

## 7. Primary keys: integers vs UUIDs

> **In short:** Integer ids are the default. Use UUIDs (`:binary_id`) when ids shouldn't be guessable or are generated outside the database.

```bash
mix phx.new my_app --binary-id      # UUIDs everywhere from the start
```

```elixir
@primary_key {:id, :binary_id, autogenerate: true}
@foreign_key_type :binary_id
schema "tasks" do ... end
```

```elixir
# migration
create table(:tasks, primary_key: false) do
  add :id, :binary_id, primary_key: true
  add :user_id, references(:users, type: :binary_id)
end
```

Trade-offs: UUIDs aren't guessable or enumerable and can be generated by clients. But they're bigger, and random UUIDs scatter index inserts (UUIDv7 or a time-ordered generator helps). You can also keep integer keys and expose a separate public `slug` or `uuid` column.

## 8. Custom Ecto types

> **In short:** Implement `Ecto.Type` to control how a value is cast from params, stored in the DB and loaded back. For example, always lowercasing emails, or a `Money` value.

```elixir
defmodule MyApp.Types.LowercaseString do
  use Ecto.Type
  def type, do: :string

  def cast(value) when is_binary(value), do: {:ok, String.downcase(String.trim(value))}
  def cast(_), do: :error

  def load(value), do: {:ok, value}
  def dump(value) when is_binary(value), do: {:ok, value}
  def dump(_), do: :error
end

# schema: field :email, MyApp.Types.LowercaseString
```

Built-in helpers: `Ecto.Enum` (atoms stored as strings or integers), `:map`, `{:array, :string}`, `:decimal`, `:binary`. Postgres also supports the citext extension (case-insensitive text), which `phx.gen.auth` uses for emails.

## 9. Soft deletes

> **In short:** Instead of deleting rows, set `deleted_at`, and filter deleted rows out of normal queries.

```elixir
field :deleted_at, :utc_datetime

def soft_delete(task), do: task |> change(deleted_at: DateTime.utc_now(:second)) |> Repo.update()

def not_deleted(query \\ Task), do: where(query, [t], is_nil(t.deleted_at))
```

Remember: unique indexes must ignore deleted rows (`create unique_index(:tasks, [:title], where: "deleted_at IS NULL")`), and you need a plan for permanent deletion (GDPR).

## 10. Multi-tenancy

> **In short:** Either add a `tenant_id`/`org_id` column to every table (simplest and most common), or give each tenant its own Postgres schema using Ecto's `prefix` option.

| Approach | How | Pros | Cons |
| --- | --- | --- | --- |
| **Foreign key** (`org_id` everywhere) | Filter every query by org, via the Phoenix 1.8 scope | Simple, one migration path, easy cross-tenant reports | A missed filter leaks data, so enforce it |
| **Schema per tenant** | `Repo.all(Task, prefix: "tenant_acme")` | Strong isolation | Migrations per tenant, harder at scale |
| **Database per tenant** | Dynamic repos | Strongest isolation | Operationally heavy |

Enforce the foreign-key approach centrally with Repo's `prepare_query/3` callback:

```elixir
defmodule MyApp.Repo do
  use Ecto.Repo, otp_app: :my_app, adapter: Ecto.Adapters.Postgres
  require Ecto.Query

  @impl true
  def prepare_query(_operation, query, opts) do
    cond do
      opts[:skip_org_id] || opts[:schema_migration] -> {query, opts}
      org_id = opts[:org_id] -> {Ecto.Query.where(query, org_id: ^org_id), opts}
      true -> raise "expected org_id or skip_org_id to be set"
    end
  end
end

Repo.all(Task, org_id: scope.org.id)
```

## 11. Migrations in depth

```elixir
# Reversible changes
alter table(:tasks) do
  add :priority, :string, default: "medium", null: false
  modify :title, :string, size: 200, from: :string    # `from:` keeps it reversible
  remove :legacy_field, :string                       # give the type so rollback can recreate it
end

rename table(:tasks), :desc, to: :description
create index(:tasks, [:project_id, :status])
create index(:tasks, [:title], where: "deleted_at IS NULL", name: :active_task_titles)
create constraint(:tasks, :priority_valid, check: "priority IN ('low','medium','high')")

# Raw SQL with an explicit rollback
execute "CREATE EXTENSION IF NOT EXISTS citext", "DROP EXTENSION IF EXISTS citext"

# Big tables: build the index without locking writes
@disable_ddl_transaction true
@disable_migration_lock true
def change, do: create index(:events, [:user_id], concurrently: true)
```

**Data migrations:** don't use your app's schema modules inside migrations (they'll change over time). Use `execute` with SQL, or `Repo.update_all` with plain table names (`from(t in "tasks", update: [set: [priority: "medium"]])`). For huge tables, backfill in batches with a separate task or an Oban job.

## Interview questions

<details>
<summary>put_assoc vs cast_assoc?</summary>

`cast_assoc` takes nested **params** for an association and runs each child's changeset, which is ideal for nested forms where the user edits children. `put_assoc` sets the association to structs, changesets or maps you already have, without casting params. For example, attaching existing tags to a task. Both need the association preloaded, and `on_replace` controls what happens to removed children.

</details>

<details>
<summary>How do you implement "insert or update" safely?</summary>

With a database upsert: `Repo.insert(changeset, on_conflict: ..., conflict_target: ...)` (or `insert_all` for bulk), backed by a unique index. It's a single atomic statement, so there's no race between "check if it exists" and "insert". Options include `:nothing`, `{:replace, fields}`, `:replace_all` and keyword updates such as `inc`.

</details>

<details>
<summary>Optimistic vs pessimistic locking?</summary>

Optimistic locking (`optimistic_lock/2` with a version column) lets everyone read and edit, and the update fails with `StaleEntryError` if the version changed meanwhile. It's good when conflicts are rare (editing records). Pessimistic locking (`lock: "FOR UPDATE"` in a transaction) blocks other writers on that row until you commit. It's good for critical check-then-update logic such as balances and inventory. Single atomic `update_all` statements with conditions often avoid locks entirely.

</details>

<details>
<summary>How would you build a filterable list endpoint with Ecto?</summary>

Start from a base query (scoped to the user or tenant), then compose conditions with `dynamic/2`, reducing over whitelisted params. Map sort options from a whitelist (never pass raw field names), add pagination (limit/offset or keyset), and validate the params with an embedded or schemaless changeset. Libraries such as Flop package this.

</details>

<details>
<summary>How do you do multi-tenancy in Phoenix/Ecto?</summary>

Most commonly, an `org_id` foreign key on every tenant-owned table, filtered through a scope struct passed into every context function, optionally enforced globally with Repo's `prepare_query/3`. Alternatives are Postgres schemas per tenant (Ecto's `prefix` option), with stronger isolation but per-tenant migrations, or a database per tenant using dynamic repos.

</details>
