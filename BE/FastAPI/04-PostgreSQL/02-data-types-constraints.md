# 02 · Data types and constraints

## 1. Numbers

> **In short:** Integers for counts and IDs, `NUMERIC` for exact money, floats only for approximate values.

| Type | Size | Use |
| --- | --- | --- |
| `SMALLINT` | 2 bytes (±32k) | Small ranges (priority, age) |
| `INTEGER` | 4 bytes (±2.1 billion) | General counts |
| `BIGINT` | 8 bytes | **IDs**, large counters |
| `NUMERIC(p, s)` | variable | **Exact** decimals: money, quantities. `NUMERIC(12,2)` = up to 10 digits before the point, 2 after |
| `REAL` / `DOUBLE PRECISION` | 4 / 8 bytes | Approximate floats: scientific data, measurements. ⚠️ Never for money |

### Auto-incrementing IDs

> **In short:** Identity columns generate IDs; expect gaps.

```sql
id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY      -- ✅ modern, SQL standard
id BIGSERIAL PRIMARY KEY                                -- older shorthand (creates a sequence)
```

`GENERATED ALWAYS` rejects manual values (use `OVERRIDING SYSTEM VALUE` when seeding with explicit IDs); `GENERATED BY DEFAULT` allows them. IDs can have **gaps** (rolled-back inserts still consume numbers): never rely on them being consecutive.

## 2. Text

> **In short:** Use `TEXT` by default, with a CHECK constraint if you need a length limit.

| Type | Notes |
| --- | --- |
| `TEXT` | Any length. **Use this by default** |
| `VARCHAR(n)` | Text with a maximum length (same performance as TEXT) |
| `CHAR(n)` | Fixed length, space-padded: avoid |

Prefer `TEXT` + a `CHECK (length(col) <= n)` constraint if you need a limit. For case-insensitive uniqueness (emails), use a unique index on `lower(email)` or the `citext` extension.

## 3. Boolean

> **In short:** True/false/NULL values.

`BOOLEAN`: `true`, `false`, `NULL`. Accepts `'t'`, `'yes'`, `'1'`, etc. as input.

## 4. Dates and times

> **In short:** Use `TIMESTAMPTZ` for moments in time, `DATE` for calendar dates, `INTERVAL` for durations.

| Type | Stores | Use |
| --- | --- | --- |
| `TIMESTAMPTZ` | A moment in time (stored as UTC, shown in the session time zone) | **Default for timestamps**: `created_at`, events |
| `TIMESTAMP` (without time zone) | Date + time with no zone | Rarely; "wall clock" values like "store opens 09:00" combined with a separate zone |
| `DATE` | Calendar date | Birthdays, due dates |
| `TIME` | Time of day | Opening hours |
| `INTERVAL` | Duration | `interval '2 hours 30 minutes'` |

```sql
SELECT now();                                     -- TIMESTAMPTZ, start of the transaction
SELECT now() AT TIME ZONE 'Asia/Kolkata';         -- convert to local wall time
SELECT '2026-11-10 10:00+05:30'::timestamptz;
SELECT date_trunc('day', now()), now() - interval '7 days', CURRENT_DATE + 30;
SELECT extract(epoch FROM now());                 -- Unix seconds
```

⚠️ Use `TIMESTAMPTZ` for real moments in time. Keep the server/session time zone at UTC and convert in the app/UI.

## 5. UUID

> **In short:** Globally unique IDs; time-ordered UUIDv7 indexes better than random v4.

```sql
id UUID PRIMARY KEY DEFAULT gen_random_uuid()        -- random UUIDv4 (built in since PG 13)
id UUID PRIMARY KEY DEFAULT uuidv7()                 -- time-ordered (built in from PG 18; use an extension or generate in the app before that)
```

UUIDv7 keeps index inserts ordered (better performance than random v4).

## 6. Enums vs CHECK vs lookup tables

> **In short:** Three ways to restrict a column to allowed values, and their trade-offs.

```sql
-- Enum type
CREATE TYPE task_status AS ENUM ('todo', 'in_progress', 'done');
ALTER TYPE task_status ADD VALUE 'archived';      -- adding is easy; removing/renaming values is hard

-- CHECK constraint (easier to change)
status TEXT NOT NULL CHECK (status IN ('todo', 'in_progress', 'done'))

-- Lookup table (when values have extra data or change often)
CREATE TABLE statuses (code TEXT PRIMARY KEY, label TEXT NOT NULL, sort_order INT);
status TEXT NOT NULL REFERENCES statuses(code)
```

Many teams prefer `TEXT + CHECK` for flexibility.

## 7. Arrays

> **In short:** Lists in a single column, with containment operators and GIN indexes.

```sql
CREATE TABLE articles (id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY, tags TEXT[] NOT NULL DEFAULT '{}');

INSERT INTO articles (tags) VALUES (ARRAY['python', 'fastapi']), ('{sql,postgres}');
SELECT * FROM articles WHERE 'python' = ANY(tags);           -- contains an element
SELECT * FROM articles WHERE tags @> ARRAY['python'];         -- contains all (GIN-indexable)
SELECT * FROM articles WHERE tags && ARRAY['sql', 'go'];      -- overlaps
SELECT id, unnest(tags) AS tag FROM articles;                 -- one row per element
UPDATE articles SET tags = array_append(tags, 'new') WHERE id = 1;
SELECT cardinality(tags) FROM articles;
```

Arrays are handy for simple lists (tags). If you need to join, count or add data per item, use a separate table.

## 8. JSON and JSONB

> **In short:** Store flexible documents as JSONB, query them with operators, and index them with GIN.

| | `JSON` | `JSONB` |
| --- | --- | --- |
| Storage | Text as written | Binary, parsed |
| Keeps key order/duplicates/whitespace | ✅ | ❌ |
| Indexable, fast operators | ❌ | ✅ |
| Use | Rarely | **Almost always** |

```sql
CREATE TABLE events (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    type TEXT NOT NULL,
    payload JSONB NOT NULL DEFAULT '{}'
);

INSERT INTO events (type, payload) VALUES
  ('signup', '{"user_id": 7, "plan": "pro", "utm": {"source": "google"}}');

SELECT payload -> 'utm' FROM events;                 -- JSONB value: {"source": "google"}
SELECT payload ->> 'plan' FROM events;               -- text: pro
SELECT payload #>> '{utm,source}' FROM events;       -- nested path as text
SELECT * FROM events WHERE payload ->> 'plan' = 'pro';
SELECT * FROM events WHERE payload @> '{"plan": "pro"}';   -- containment (GIN-indexable)
SELECT * FROM events WHERE payload ? 'utm';                -- key exists
SELECT (payload ->> 'user_id')::bigint FROM events;        -- cast extracted text

UPDATE events SET payload = payload || '{"verified": true}' WHERE id = 1;       -- merge
UPDATE events SET payload = jsonb_set(payload, '{utm,source}', '"bing"') WHERE id = 1;
UPDATE events SET payload = payload - 'verified' WHERE id = 1;                  -- remove key

SELECT jsonb_build_object('id', id, 'type', type) FROM events;      -- build JSON in SQL
SELECT jsonb_agg(t) FROM (SELECT id, title FROM tasks LIMIT 3) t;    -- rows → JSON array
```

**When to use JSONB:** truly variable attributes, external API payloads, settings, event data. **When not to:** data you filter, join, or constrain often: give it real columns (you get types, constraints, FKs, simpler queries and better statistics).

## 9. Other useful types

> **In short:** Binary, network, range, full-text, geospatial and vector types.

| Type | Use |
| --- | --- |
| `BYTEA` | Binary data (small files). Store large files in object storage and keep the URL in the DB |
| `INET`, `CIDR`, `MACADDR` | IP addresses and networks |
| Range types: `int4range`, `tstzrange`, `daterange` | Booking periods; with exclusion constraints to prevent overlaps |
| `TSVECTOR` | Full-text search documents (lesson 03) |
| Geometric / PostGIS `geometry`, `geography` | Locations, maps |
| `vector` (pgvector) | Embeddings for AI similarity search |

```sql
-- No overlapping room bookings
CREATE EXTENSION IF NOT EXISTS btree_gist;
CREATE TABLE bookings (
    room_id BIGINT NOT NULL,
    during TSTZRANGE NOT NULL,
    EXCLUDE USING gist (room_id WITH =, during WITH &&)
);
```

## 10. Constraints

> **In short:** NOT NULL, UNIQUE, CHECK, foreign keys, exclusion constraints and generated columns.

```sql
CREATE TABLE products (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    sku TEXT NOT NULL,
    name TEXT NOT NULL CHECK (length(name) BETWEEN 1 AND 200),
    price NUMERIC(10, 2) NOT NULL CHECK (price >= 0),
    sale_price NUMERIC(10, 2),
    category_id BIGINT REFERENCES categories(id) ON DELETE SET NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT products_sku_key UNIQUE (sku),
    CONSTRAINT sale_below_price CHECK (sale_price IS NULL OR sale_price < price)
);
```

| Constraint | Notes |
| --- | --- |
| `NOT NULL` | Use on most columns |
| `DEFAULT` | Value when none given |
| `UNIQUE` | ⚠️ Multiple NULLs are allowed by default; `UNIQUE NULLS NOT DISTINCT` (PG 15+) treats NULLs as equal |
| `CHECK` | Any boolean expression on the row |
| `PRIMARY KEY` | UNIQUE + NOT NULL |
| `FOREIGN KEY` / `REFERENCES` | With `ON DELETE`/`ON UPDATE` actions. Index the FK column yourself |
| `EXCLUDE` | Generalized uniqueness (no overlapping ranges) |
| Generated columns | `total NUMERIC GENERATED ALWAYS AS (qty * price) STORED` |

**Name your constraints** (`CONSTRAINT products_sku_key UNIQUE (sku)`) so error messages and migrations are readable.

### Partial unique index (unique among some rows)

> **In short:** Enforce uniqueness only where a condition holds (e.g. non-deleted rows).

```sql
CREATE UNIQUE INDEX users_email_active_key ON users (lower(email)) WHERE deleted_at IS NULL;
```

### Adding constraints to existing big tables without long locks

> **In short:** Add as `NOT VALID`, then `VALIDATE` without blocking writes.

```sql
ALTER TABLE orders ADD CONSTRAINT orders_total_positive CHECK (total >= 0) NOT VALID;  -- quick, checks new rows
ALTER TABLE orders VALIDATE CONSTRAINT orders_total_positive;                          -- scans without blocking writes
```
